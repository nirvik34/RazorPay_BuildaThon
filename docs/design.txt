````md
# Design System: AgentPay Guard

## Overview

AgentPay Guard is a local-first financial security and consent layer for autonomous AI agents.

The interface should communicate one central idea:

> **AI can act. The user remains in control of money.**

The visual language combines:

- financial infrastructure
- cybersecurity
- AI agent activity
- human approval
- transaction transparency

The product should feel like a serious security product rather than a generic AI dashboard.

It should not look like a banking clone, cryptocurrency dashboard, or chatbot interface.

---

# 1. Design Philosophy

## 1.1 Trust Before Intelligence

The most important information is not the AI's reasoning.

It is:

1. What is the agent trying to do?
2. How much money is involved?
3. Where is it going?
4. Why is the action being requested?
5. What will happen if I approve?
6. What happens if I reject?

The interface therefore prioritizes transaction context over decorative AI elements.

---

## 1.2 Human-in-the-Loop

The product's defining interaction is:

```text
AI REQUEST
     ↓
GUARD EVALUATION
     ↓
USER DECISION
     ↓
AUTHORIZED / BLOCKED
````

The UI must make the decision point extremely obvious.

Approval and rejection should never look like secondary actions.

---

## 1.3 Security Without Fear

AgentPay Guard is a security product, but the UI should not constantly scream "danger."

Use:

* neutral states for normal activity
* amber for attention
* red only for actual rejection, blocking, or critical threats
* green for successful authorization

This creates a visual language users can learn quickly.

---

## 1.4 Local-First

The Android app is the trusted device.

The design should subtly reinforce:

```text
THIS DEVICE
     ↓
YOUR POLICIES
     ↓
YOUR AUTHORITY
     ↓
YOUR DECISION
```

Cloud synchronization should never visually imply that the cloud is the authority over the user's money.

---

## 1.5 Infrastructure Precision

Borrow the useful qualities of financial infrastructure products:

* tight spacing
* clear grids
* thin borders
* compact tables
* strong numerical hierarchy
* deterministic status labels
* explicit timestamps
* transaction IDs
* audit trails

Avoid unnecessary gradients, glassmorphism, excessive rounded cards, and decorative illustrations.

# 42. Security Indicators

Use a compact device status:

```text
● DEVICE PROTECTED
```

Possible states:

```text
● PROTECTED
● SYNCING
● OFFLINE
● ACTION REQUIRED
● SECURITY ALERT
```

Offline is not an error.

Show:

```text
OFFLINE
Local protection active
```

This reinforces the local-first architecture.

When disconnected:

```text
┌─────────────────────────────────┐

│ checks continue on this device. │
│                                 │
```

Never imply:

# 44. Design Rules

## Do

* make amounts visually prominent
* explain every security decision
* distinguish user rejection from policy blocking
* show agent identity
* show user intent
* show merchant
* show exact reason
* make Accept/Reject obvious
* keep audit records readable
* use green/red semantic states consistently
* prioritize operational clarity

## Don't

* use excessive gradients
* use giant AI robot illustrations
* use glowing neon cyberpunk visuals
* turn everything into a card
* hide rejection reasons
* make the dashboard more important than the approval experience
* let an LLM decision look authoritative
* use red for ordinary warnings
* make cloud connectivity look like the security boundary
* copy Razorpay's branding

AgentPay Guard should feel like:

```text
Financial infrastructure
        +

        +
AI agent control
```

Not:

```text
Crypto dashboard
        or
Generic AI SaaS
        or
Traditional banking app
```

# 46. Brand Voice

Interface copy should be:

* short
* factual
* specific
* non-alarmist
* action-oriented

Bad:

> "Uh-oh! Your AI is trying something suspicious!"

Good:

> **Potential policy circumvention detected.**

Bad:

> "Your payment is super safe!"

Good:

> **Policy checks passed. User approval required.**

Bad:

> "Oops!"

Good:

> **Authorization denied. No payment was attempted.**

# 47. Primary Design Principle

Every important screen should make this sequence understandable:

```text
WHAT DOES THE AI WANT?
          ↓
WHY?
          ↓
IS IT ALLOWED?
          ↓
WHAT IS THE RISK?
          ↓
WHAT CAN I DO?
          ↓
WHAT HAPPENED?
```

If a user can answer those six questions, the interface is doing its job.

# 50. Final Design Direction

AgentPay Guard should look like the **security layer that agentic commerce was missing**.

The visual hierarchy is:

```text
              TRUST
                │
                ▼
          USER DECISION
                │
       ┌────────┴────────┐
       ▼                 ▼
    APPROVE             REJECT
      GREEN               RED
       │                  │
       ▼                  ▼
   AUTHORIZED           BLOCKED
       │
       ▼
    RAZORPAY
```

The AI is visually secondary.

The payment amount and user decision are primary.

The Guard's reasoning is visible but concise.

The audit trail is precise.

The Android device is the trusted local authority.

The web dashboard is the operational control plane.

That is the visual identity of **AgentPay Guard**.
